# SOLUTION

## Скидки

В заказы добавил `amount_paid_kop` (миграция `002_amount_paid.sql`).

При разборе ответа внешнего API читаю `amountPaid`. Если поля нет (старые заказы / начало выборки) — пишу ту же сумму, что и в `amount`, т.е. скидки нет. `discountPercent` не использую: по факту оплачено лежит в `amountPaid`, процент только для справки.

В `daily-totals` теперь:

- `gross` — сумма `amount` по paid
- `net` — сумма `amountPaid`
- `discount` — разница
- `total` = `gross` (как просили, для совместимости)

Считаю в копейках, в ответ отдаю рубли. `discount` тоже из копеек, чтобы не ловить расхождения на float.

## Жалоба по c_7 (27–31.03)

Сначала посмотрел клиента: `GET /customers/c_7` → `Europe/Berlin`.

В `TotalsService` offset брался один раз: `tzOffsetMinutes(timezone, new Date())`, и этим же числом размечались все заказы. Для Москвы это почти незаметно, для Берлина в конце марта — нет: 29.03.2026 перевод CET→CEST. Заказы около полуночи UTC уезжали на соседний календарный день, отсюда «часть дней не сходится, остальные до копейки».

Исправил просто: для каждого заказа беру offset на его `createdAt`, а не на «сейчас».

## Заметки по ходу

- `amountPaid` / `discountPercent` в листинге заказов появляются не сразу, а примерно с середины данных (~15 марта). До этого поля просто нет.
- Rate limit иногда приходит как `200 { error: "rate_limited" }` — в клиенте уже обработано.
- В конце синка курсор иногда «зацикливается» на пустой странице — в коде это тоже уже учтено.
- `POST /sync` без `Content-Type: application/json` Fastify не принимает.

## Допущения

- Нет `amountPaid` → скидка 0.
- День по-прежнему от `createdAt`, только paid.
- `toKop` как было — `Math.floor`, доли копейки отбрасываем.

## Если бы было больше времени

Вынести группировку по дням в SQL (`AT TIME ZONE`), меньше таскать заказы в Node. И нормально подхватывать `.env` при старте — сейчас файл сам по себе в process.env не попадает.
